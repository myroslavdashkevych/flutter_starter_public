# Architecture

Clean Architecture layers at the top level; business areas (domain, data) and
user flows (features) inside them.

This file holds the rules every change needs: structure, import rules and each
cross-cutting pattern in its own section. Details of each area are in [areas/](areas/); the
reasons behind decisions are in [ADRs](../decisions/).

## Principles

1. **Dependencies point inward.** `presentation` and `data` depend on `domain`;
   `domain` depends on nothing but pure Dart.
2. **Data is organized by business area, UI by user flow.** One repository per
   business area is shared by any number of features.
3. **`app` is the only module that knows everything.** It wires DI, routing and
   bootstrap.
4. **Shared code respects layer rules.** Code shared inside a layer lives in that
   layer's `_shared/` folder, so layer rules apply to it automatically.
5. **Promote on second use.** Code moves to `_shared/` only when a second
   consumer needs it.

## Folder structure

```
lib/
  main.dart                     # entry point: calls bootstrap()
  app/                          # composition root: app.dart, bootstrap.dart, locale resolution
    di/                         # @InjectableInit, modules that need flavor config
    router/                     # GoRouter, typed route tree, auth redirect, screen views
    firebase/                   # generated by flutterfire (do not read)
    config/                     # AppConfig, AppInfo, Flavor
    links/                      # opens a web page with url_launcher, with fallbacks
    observability/              # error handlers, Talker observer, crash report user id
    notifications/              # FCM background handler, wiring of subscriptions and taps
  shared/                       # cross-layer only
    logging/                    # Talker factory and helpers
    utils/                      # pure Dart extensions and helpers
  domain/
    _shared/                    # Result, Failure, Paginated
      services/                 # ports: AnalyticsService, CrashReportingService
    auth/
    items/
    favorites/
    settings/
    notifications/
  data/
    _shared/
      network/                  # Dio factories, interceptors, TokenProvider, safeCall
      storage/                  # Hive init, SharedPreferencesAsync provider, ExpiringCache
      services/                 # port implementations: FirebaseAnalyticsService, FirebaseCrashReportingService
    auth/
    items/
    favorites/
    settings/
    notifications/
  presentation/
    _shared/                    # layout: Inside presentation/_shared
      theme/                    # AppTheme light/dark (Material 3)
      l10n/                     # context.l10n extension, failure -> message mapping
      bloc/
        favorite/               # favorite toggle Cubit and state
      widgets/
        button/                 # favorite toggle
        dialog/                 # dialog shown before the system notification permission request
        item/                   # item tile and its image
        state/                  # failure view with retry
    auth/                       # sign in, sign up, reset password
    items_list/
    item_details/
    favorites/                  # favorites list, removal of a missing favorite
    profile/                    # guest or account view, sign out, delete account
    settings/
    home_shell/                 # bottom navigation: Items, Profile, Settings
  l10n/
    arb/                        # app_en.arb (template), app_uk.arb
    gen/                        # generated AppLocalizations

test/                           # tests (paths: Naming); not every file has a test
tool/                           # import rule and spec checkers (CI), new project init script, review diff tool
config/                         # non-secret runtime config per flavor
```

A folder without tracked files keeps a `.gitkeep`; remove it once the folder has one.

### Inside a domain area (`domain/<area>/`)

```
entities/          # freezed classes, no JSON
repositories/      # abstract repository contracts (always present)
usecases/          # all use cases of this area (optional)
```

### Inside a data area (`data/<area>/`)

```
datasources/       # *_remote_data_source.dart, *_local_data_source.dart, *_api.dart
models/            # *_dto.dart (freezed + json) and mappers to entities
repositories/      # *_repository_impl.dart
```

### Inside a feature (`presentation/<feature>/`)

```
bloc/              # *_bloc.dart / *_cubit.dart, *_event.dart, *_state.dart
pages/             # *_page.dart (one per route)
widgets/           # feature-private widgets
```

### Inside `presentation/_shared`

Two special-purpose folders, `theme/` and `l10n/`; everything else follows the layout of a
feature, so a reader learns one layout. Subfolder names are singular, and a folder is created
with its first file.

```
theme/             # AppTheme light/dark
l10n/              # context.l10n extension, failure -> message mapping
bloc/<subject>/    # Cubits and BLoCs used by several features, by what they manage: favorite/
pages/<subject>/   # pages used by several features (none yet)
widgets/<type>/    # widgets used by several features, by widget type: button/, dialog/, item/, state/
```

A widget of an area that has no feature of its own, shown only by `app`, also lives here
(for example the notification permission dialog in `widgets/dialog/`): it belongs to the
area, not to the screen that shows it, so removing the area does not touch that screen.

## Import rules

Enforced by `tool/check_imports.dart` in CI.

### Between top-level modules

| Module | May import | Must not import |
|---|---|---|
| `shared/` | allowed packages (External packages) | any layer, `app`, `l10n` |
| `domain/**` | `shared/`, `domain/**` (see below), allowed packages | `data`, `presentation`, `app`, `l10n`, Flutter, `dart:ui`, `dart:io`, `dart:ffi`, `dart:isolate`, `dart:html` |
| `data/**` | `shared/`, `domain/**`, `data/_shared`, its own packages | `presentation`, `app`, `l10n`, presentation packages, Flutter UI |
| `presentation/**` | `shared/`, `domain/**`, `presentation/_shared`, `l10n`, its own packages | `data`, `app`, data packages |
| `l10n/` | `flutter`, `flutter_localizations`, `intl` | everything else |
| `app/` | everything | — |

`main.dart` counts as `app`. Files outside these modules are rejected.

### Libraries and code

- `data` may use only `flutter/foundation.dart` and `flutter/services.dart` from
  Flutter: no widgets in data.
- BLoC files (`*_bloc.dart`, `*_cubit.dart`, `*_state.dart`, `*_event.dart`) may use
  only `flutter/foundation.dart` from Flutter, so they never see a `BuildContext`.
- `getIt`, `GetIt` and `GetItHelper` appear only in `app/`. The checker
  searches the code for these names, because `injectable.dart` re-exports
  `GetItHelper`.

### File locations

- Files named `*_dto.dart` and `*_repository_impl.dart` live in `data`,
  `*_use_case.dart` in `domain/<area>/usecases`, `*_bloc.dart` and `*_cubit.dart` in
  `presentation`.
- No `usecases` folder under `presentation/`.

### Inside a layer

- `<layer>/<x>` may import `<layer>/_shared`.
- `<layer>/_shared` must not import any area or feature of its layer.
- Areas of one layer must not import each other: `data/items` must not import
  `data/auth`.
- Features must not import each other: `presentation/items_list` must not import
  `presentation/item_details`. When one screen needs data from several areas, it
  stays one feature with several BLoCs/Cubits, each depending on its own domain
  repository.
- **Exception:** `domain/<area>` may import entities of another `domain/<area>`
  when one entity references another. Keep this rare.
- **Exception:** `domain/<area>/usecases` may import repository contracts of
  another `domain/<area>`, so a use case can combine several areas. It must not
  import use cases of another area.
- Any feature may import any `domain/<area>`.

### Reserved names

`shared` and `_shared` are reserved and cannot be used as area or feature names.

### External packages

Each module gets one of two policies:

- **Allow list** for `shared`, `domain` and `l10n`: only the listed packages
  (`_allowedPackages` in `tool/check_imports.dart`). `shared`: `injectable`, `talker`,
  `meta`, `collection`. `domain`: `freezed_annotation`, `meta`, `collection`, and from
  `injectable` only `package:injectable/injectable.dart` (annotations for use cases).
- **Package ownership** for `data` and `presentation`. Every package belongs to one of
  them, and the other layer must not import it:
  - **Default:** the layer that imports a package owns it. A new UI package (an
    animation or image library) or a new data package (an SDK, a database) needs no
    change in the checker.
  - **Both layers:** a package imported by both fails the check unless it is listed in
    `_sharedPackages`: `flutter`, `freezed_annotation`, `injectable`,
    `stream_transform`, `meta`, `collection`.
  - **Known owners:** `_knownOwners` names packages whose layer is clear in advance, so
    a first import in the wrong layer fails too. Data: `dio`, `http`, `retrofit`,
    `hive_ce`, `hive_ce_flutter`, `shared_preferences`, `sqflite`, `drift`,
    `firebase_*`. Presentation: `flutter_bloc`, `bloc`.

When you add a package, decide its layer:

1. Does it reach the network, storage, a platform SDK or Firebase? It belongs to
   `data`; add it to `_knownOwners` if it is widely known.
2. Does it draw UI or hold UI state? It belongs to `presentation`.
3. Do both layers really need it (annotations, pure utilities)? Add it to
   `_sharedPackages`. Keep this list short: every entry is a link between the layers.
4. Only `app` uses it (startup, links, app info)? No change: `app` is unrestricted.

## Data flow

```
Page -> Bloc/Cubit -> [UseCase] -> Repository (domain, abstract)
                                        ^
                       RepositoryImpl (data) -> RemoteDataSource (retrofit / Firebase)
                                             -> LocalDataSource (hive_ce / prefs)
```

- A BLoC may call a repository directly when there is no business logic.
- A use case is added when logic exists: combining repositories, validation,
  business rules. It stays in its domain area (File locations), even when only
  one feature uses it. A use case spanning several areas lives in the area
  of its main responsibility and depends on the other areas' repository
  contracts.
- The `items` area intentionally includes use cases as a reference example.

## Result and failure

`Result` and `Failure` live in `domain/_shared`.

```dart
sealed class Result<T> {
  const Result();
}

final class Ok<T> extends Result<T> {
  const Ok(this.value);
  final T value;
}

final class Err<T> extends Result<T> {
  const Err(this.failure);
  final Failure failure;
}
```

`Failure` is a sealed hierarchy with variants such as `NetworkFailure`,
`ServerFailure(statusCode)`, `NotFoundFailure`, `CacheFailure`, `AuthFailure`
(with an `AuthFailureReason` enum), `UnexpectedFailure`.

Why an own `Result`: [ADR-006](../decisions/ADR-006-models-and-errors.md).

Rules:
- Repositories return `Result<T>` or `Stream<T>`; they never throw.
- Exceptions are converted to `Failure` only in `data`, in one place:
  `safeCall()` in `data/_shared/network` plus area-specific mappers
  (for example, `FirebaseAuthException` -> `AuthFailure`).
- Failures are turned into user messages only in `presentation/_shared/l10n`.
- Errors are never swallowed silently.

## Entities and DTOs

| | Location | Tools | JSON |
|---|---|---|---|
| Entity | `domain/<area>/entities` | freezed | No |
| DTO | `data/<area>/models` | freezed + json_serializable | Yes |
| Mapper | `data/<area>/models` | extension `toEntity()` / `fromEntity()` | — |

freezed 4 rules: classes are `sealed` or `abstract`; no `final` keyword on
constructor parameters. Why freezed: [ADR-006](../decisions/ADR-006-models-and-errors.md).

## Paginated data

`Paginated<T>` in `domain/_shared`: `items`, `page`, `hasMore`.
Pagination details of a specific API stay in `data`.

## Dependency injection

Why get_it + injectable: [ADR-002](../decisions/ADR-002-get-it-injectable.md).

- Registration with annotations next to each class.
- Repositories: `@LazySingleton(as: XRepository)`.
- BLoCs and Cubits: `@injectable` (factory), created in the route builders in
  `app/router/routes.dart` via `BlocProvider(create: (_) => getIt<XBloc>())`.
- Global singletons: `AuthBloc`, `SettingsCubit` (`@lazySingleton`). `app` provides
  `SettingsCubit` above `MaterialApp` and passes `AuthBloc` to the router, its only
  reader. Other features never read them; they depend on the domain repositories
  instead.
- Third-party objects (Dio, Talker, SharedPreferencesAsync, Hive boxes) are provided
  by `@module` classes in `data/_shared` and `shared/` (or `app/di` when they need
  flavor config). `FirebaseAuth` is provided in `data/auth`, the only area that
  imports it.
- Classes receive dependencies through constructors; where `getIt` may appear is in
  Import rules, Libraries and code.
- `getIt.init` receives the flavor name as the environment. No registration uses
  `@Environment` yet; add it when a class differs per flavor.

## State management

Why BLoC: [ADR-001](../decisions/ADR-001-flutter-bloc.md).

- `Cubit` for simple state; `Bloc` when events need transformers
  (debounce, droppable, restartable).
- States are freezed sealed classes or a single freezed class with a status enum.
- BLoCs depend on repositories or use cases, never on data sources.

## Routing

Uses go_router + go_router_builder. Why these rules:
[ADR-003](../decisions/ADR-003-go-router.md). Route map and redirect behavior:
[features/navigation.md](features/navigation.md).

- The typed route tree lives in `app/router/routes.dart`, because nested typed
  routes must be declared in one tree.
- Features expose pages; `app` assembles them into routes.
- **Features never navigate by themselves.** A page receives navigation callbacks
  in its constructor (for example `onItemSelected(int id)`), and the route
  builder in `app/router/routes.dart` implements them with typed routes
  (`ItemDetailsRoute(id: id).go(context)`). This keeps features free of `app`
  imports and of each other.
- Routes and navigation callbacks take ids, never whole domain objects.
- A page that shows a widget with its own Cubit, such as the favorite toggle on each
  tile, takes a builder in its constructor. The route builder implements it with
  `BlocProvider(create: (_) => getIt<...>())`, because `presentation` cannot reach
  `getIt`. The same way, a page takes an optional builder for an action from another
  feature.
- `AuthBloc` is read by the top-level redirect on each navigation, only to keep
  signed-in users off the auth routes. The router has no `refreshListenable`: auth
  changes do not navigate, the Profile page follows them through `ProfileCubit`.
- Screen views are sent by `ScreenViewObserver` in `app/router`, not
  `FirebaseAnalyticsObserver` (ADR-003), with route names that carry no ids. How it is
  attached and what counts as a screen: [areas/observability.md](areas/observability.md),
  Screen views.

## Networking

Why dio + retrofit and two clients: [ADR-004](../decisions/ADR-004-dio-retrofit.md). Why the
retry rules: [ADR-005](../decisions/ADR-005-retry-policy.md).

- Two Dio clients, both created in `data/_shared/network`:
  - `publicDio` for third-party public APIs. **No auth header.**
  - `backendDio` for the app's own backend. Has `AuthInterceptor`.
- Both clients have connect and receive timeouts (`dio_factory.dart`); a timeout
  becomes `NetworkFailure`. A slow request overrides them through its own `Options`.
- **Never** attach the Firebase ID token to a third-party API.
- A 401 from the own backend refreshes the token once and retries; a second 401 signs the
  user out.
- Only GET and HEAD are retried, and only for transient errors, with a short bounded
  backoff.
- `TokenProvider` is an abstract class in `data/_shared/network`;
  `data/auth` implements it with Firebase Auth.
- Network logs never contain the `Authorization` header and, in prod, no bodies.
- Details (interceptor steps, retried statuses, numbers, chain order):
  [areas/network.md](areas/network.md).

## Local storage

| Data | Kind | Storage | Why |
|---|---|---|---|
| Settings (theme, locale, usage data sharing) | Settings | `SharedPreferencesAsync` | Few scalar values, needed at startup |
| Notification permission flag (`notifications.permission_requested`) | Settings | `SharedPreferencesAsync` | One boolean |
| Items (API responses) | Cache | hive_ce `LazyBox`, JSON strings ([areas/items.md](areas/items.md)) | Many records, TTL, keyed by request |
| Favorites | User data | hive_ce `LazyBox` per user, JSON strings ([areas/favorites.md](areas/favorites.md)) | Persistent snapshots of items, separated by user |

### Cache or user data

Every Hive store is one of two kinds. Decide before writing the data source by asking:
**if this data is lost, can it be fetched again?** Yes: a cache. No: user data. When
unsure, treat it as user data ([ADR-008](../decisions/ADR-008-cache-or-user-data.md)).

| | Cache (example: items) | User data (example: favorites) |
|---|---|---|
| Origin | A copy of server data | Created by the user; no other copy |
| Marker in code | Data source `implements ExpiringCache` | Doc comment "User data"; never `ExpiringCache` |
| Box | Its own, named `<area>_cache` | Its own; never shared with a cache |
| Storage failure | Logged; the record counts as missing | Reaches the caller |
| Automatic deletion | Yes: records older than the cache's `maxAge` (set in its area file), with another `schemaVersion` or unreadable, after startup | **Never** |
| Who deletes | The app | Only a user action (remove a favorite, delete the account) |
| DTO change | Bump `schemaVersion`; old records are ignored, then evicted | Stay backward compatible (`@JsonKey(defaultValue: ...)`) or ship a migration; an unreadable record is skipped, logged and kept |

- Every cache is listed in `_evictExpiredCaches` in `app/bootstrap.dart`, which runs
  `evictExpired()` after the first frame. Freshness is a separate, much shorter TTL in
  the repository; `maxAge` only limits how long stale data can still be shown offline.
- User data of a signed-in user is deleted with the account: add its cleanup to
  `DeleteAccountUseCase` ([areas/profile.md](areas/profile.md)).
- Hive values are JSON **strings** (`jsonEncode` of a DTO's `toJson()`), not maps. No Hive
  type adapters and no `hive_ce_generator` ([ADR-007](../decisions/ADR-007-local-storage.md)).
- Every stored value is wrapped in an envelope with `schemaVersion`.
- Box names are lower-cased by Hive, so a case-sensitive part of a name (a user id)
  is stored in hex.
- Each storage is wrapped by a local data source; nothing outside `data` knows
  about Hive or SharedPreferences.

## Logging and errors

- One `Talker` instance from `shared/logging`, registered in DI.
- Crash reporting and analytics sit behind the `CrashReportingService` and
  `AnalyticsService` ports in `domain/_shared/services`. `FirebaseCrashlytics` and
  `FirebaseAnalytics` are used only by their implementations in `data/_shared/services`, so
  tests never reach them.
- Fatal errors reach crash reporting through the port; each error is reported once.
- `TalkerBlocObserver` logs nothing but errors in `prod`, because states hold user data.
- Usage data is collected only when the flavor allows it and the "Share usage data" setting
  is on ([ADR-009](../decisions/ADR-009-usage-data-collection.md)).
- Mechanism (error handlers, observers, how collection is switched):
  [areas/observability.md](areas/observability.md).

## Localization

- gen-l10n with ARB files in `lib/l10n/arb`, generated code in `lib/l10n/gen`
  (not a synthetic package).
- `domain` and `data` never produce user-facing text.

## Testing

| Layer | What to test | Tools |
|---|---|---|
| domain | use cases, entity logic | `test`, mocktail |
| data | repositories (mapping, caching, failures), mappers, interceptors, data sources | mocktail, Dio mock adapter |
| presentation | BLoCs/Cubits, each state transition; widget tests for critical flows (sign-in validation, list states) | bloc_test, `flutter_test` widget tests |

- Mocks are created with mocktail; `registerFallbackValue` lives in shared test
  helpers under `test/helpers/`.
- Firebase is never called in tests; it sits behind repositories and ports.
- Test names carry requirement IDs: [docs/README.md](../README.md), Requirements.
- Test file paths: Naming (the `Test` row).

## Adding a feature

A checklist for a new feature:

1. Follow the change process ([docs/README.md](../README.md), Changes); the steps below cover
   the code.
2. Does the data belong to an existing area? If not, create `domain/<area>` with
   entities and a repository contract, then `data/<area>` with the implementation.
3. Create `presentation/<feature>` with `bloc/`, `pages/`, `widgets/`.
4. Business logic? Add a use case (Data flow).
5. Stores data locally? Classify it as a cache or user data (Local storage, Cache or user
   data) before writing the data source.
6. Needs a new package? Decide which layer owns it (Import rules, External packages).
7. Add routes in `app/router/routes.dart`.
8. Add strings to both ARB files.
9. Add tests mirroring the new files.
10. Record the implementation details in `spec/areas/<area>.md`.
11. Run [docs/README.md](../README.md), Verification, then the review.
