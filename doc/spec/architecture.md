# Architecture

Clean Architecture with three layers: `domain` split by kind, `data` by business area,
`presentation` by user flow (feature).

**Here:** the rules every change needs: principles and terms, the folder structure, import
rules, data flow, and one section per cross-cutting pattern (use cases, errors, entities, DI,
state, routing, networking, storage, logging, localization, testing).

**Not here:** how code is written inside a file and every naming rule
([code-style.md](code-style.md)); details of one area ([area/](area/)); behavior
([behavior/](behavior/)); security rules ([security.md](security.md)); packages
([tech-stack.md](tech-stack.md)); the reasons behind a
project's own decisions ([ADRs](../decision/)).

## Principles

1. **Dependencies point inward.** `presentation` and `data` depend on `domain`; `domain`
   depends on nothing but pure Dart.
2. **The UI reaches the domain only through use cases.** Use cases combine business areas;
   each area has one repository, shared by any number of use cases.
3. **`app` is the only top-level folder that knows everything.** It wires DI, routing and
   bootstrap.
4. **Shared code respects layer rules.** Code shared inside a layer lives in that layer's
   `_shared/` folder, so the layer's rules apply to it.
5. **Promote on second use.** Code moves to `_shared/` only when a second consumer needs it.
6. **One public type per file.** A file that declares public classes, enums, mixins or
   typedefs declares the one named after the file (PascalCase of the file name); its other
   public types are only its sealed variants or enums its fields use. Extensions are exempt
   from the name rule. Every public type and extension name is unique in `lib/`. The one
   exception is `app/router/routes.dart`: go_router_builder needs the route tree in one file.
7. **Interfaces by default.** A type that others implement (a port or a base class) is an
   `abstract interface class`: a contract with no code. An `abstract class` is used only where
   a library requires it (freezed classes, injectable `@module` classes, retrofit clients) or
   where the class holds code its subclasses share. `tool/check_imports.dart` checks the
   folders of ports and base classes in `domain` (`repository/`, `_shared/service/`,
   `_shared/base/`) and `data/_shared/base/`; the rest is checked in review.

## Terms

Each term has one meaning in these docs and in the code.

- **Layer**: `domain`, `data` or `presentation`.
- **Top-level folder**: a folder directly under `lib/`: the three layers, `shared`, `l10n` and
  `app`. Import rules are set per top-level folder.
- **Business area** (area): a part of the app's data with one repository contract
  (`domain/repository/<area>_repository.dart`) and one `data/<area>/` folder. `spec/area/`
  also has files for cross-cutting parts that are not business areas (`network`,
  `observability`).
- **Feature**: a user flow in `presentation/<feature>/`.
- **Port**: an `abstract interface class` that its consumer declares and another layer or
  area implements: repository contracts, services, `TokenProvider`.
- **Repository**: the port that gives access to the data of one business area.
- **Service**: a port in `domain/_shared/service/` for a cross-cutting side effect that belongs
  to no area and returns no data. Its implementation is in `data/_shared/service/`.
- **Base class**: an `abstract interface class` in `<layer>/_shared/base/` (`domain` or `data`)
  that other classes of its layer implement (`UseCase`, `StreamUseCase`, `ExpiringCache`). It
  is not a port: no other layer implements it.
- **Wrapper**: a generic type in `domain/_shared/wrapper/` that wraps values of any area
  (`Result<T>`, `Paginated<T>`).
- **Data source**: the one class that wraps one SDK, client or storage for one repository.
- **Use case**: one business action in `domain/use_case/<group>/`.
- **Use case group**: the folder of a use case, named after the business area of its result.
  It orders the domain and limits no caller.
- **DI module**: an injectable `@module` class (`<name>_module.dart`) that provides objects
  that cannot carry an annotation: SDK instances, Dio clients, values from the flavor config.
- **Component**: a shared piece of UI with its own Bloc.

## Folder structure

```
lib/
  main.dart                     # entry point: calls bootstrap()
  app/                          # composition root: app.dart, bootstrap.dart, locale resolution
    di/                         # @InjectableInit
      config_module/            # DI modules that read AppConfig
    router/                     # GoRouter, typed route tree, auth redirect, screen views
    config/                     # AppConfig, AppInfo, Flavor
      firebase/                 # generated by flutterfire (do not read)
    link/                       # opens a web page with url_launcher, with fallbacks
    observability/              # error handlers, Talker observer, crash report user id
    notification/               # FCM background handler, wiring of subscriptions and taps
  shared/                       # cross-layer only
    logging/                    # Talker factory and helpers
    utils/                      # pure Dart extensions and helpers
  domain/                       # layout: Inside domain
  data/
    _shared/                    # base/, data_source/ (network/, hive/, prefs/), service/
    auth/                       # one folder per business area; layout: Inside a data area
    character/
    favorite/
    settings/
    notification/
  presentation/
    _shared/                    # layout: Inside presentation/_shared
    auth/                       # sign in, sign up, reset password
    character_list/
    character_detail/
    favorite_list/              # favorites list, removal of a missing favorite
    profile/                    # guest or account view, sign out, delete account
    settings/
    home_shell/                 # bottom navigation: Characters, Profile, Settings
  l10n/
    arb/                        # app_en.arb (template), app_uk.arb
    gen/                        # generated AppLocalizations

test/                           # mirrors lib/ (code-style.md, Files and types); not every file has a test
tool/                           # import and spec checkers (CI), new project init script, review diff tool
config/                         # non-secret runtime config per flavor
```

A folder without tracked files keeps a `.gitkeep`; remove it once the folder has a file.

### Inside `domain`

`domain` is split by kind and has no area folders: an area exists in `domain` only as the name
of its repository contract and of its use case group. No other folder exists.

```
_shared/                 # what describes the data of no business area, by role
  base/<subject>/        # base classes: use_case/ (UseCase, StreamUseCase)
  wrapper/<subject>/     # generic wrappers: result/ (Result, Failure), pagination/ (Paginated)
  service/<subject>/     # ports for side effects: analytics/, crash_reporting/
entity/                  # freezed classes, no JSON: the entities of the business areas
repository/              # <area>_repository.dart: repository contracts
use_case/                # one group folder per business area, one use case per file
  <area>/                # auth/, character/, favorite/, notification/, settings/
  observability/         # use cases that reach only services and serve no business area
```

- **`_shared`** has three roles, each with one folder per subject: `base` (classes that other
  domain classes implement), `wrapper` (generic types that wrap values of any area) and
  `service`. A service folder holds the port and the types it takes; its implementation is in
  the folder of the same name in `data/_shared/service/`. Nothing in `_shared` belongs to an
  area: an area's entity goes to `entity/`, a use case to its group. `AuthFailureReason` stays
  in `failure.dart` as part of `Failure`.
- **A use case group** is the area of the use case's result: the area whose data it returns or
  changes. A use case that combines areas goes to the area of its result
  (`auth/delete_account_use_case.dart` also clears the favorites). A use case that reaches only
  services goes to the area of the requirement it implements
  (`character/track_search_use_case.dart`, CHR-17), or to `observability/` when that is no
  area (OBS). Any Bloc may call a use case of any group.
- **A repository** reads, stores and returns the entities of one area. Each has its own area in
  `data`.
- **A service** is a port for a cross-cutting side effect that returns no data: sending an
  analytics event, recording a crash. Analytics events are an `AnalyticsEvent` sealed class
  that names what happened in business terms; the event names and parameters sent to Firebase
  are set only by `FirebaseAnalyticsService`.
- **An entity** belongs to the area whose data it describes, or, when only a use case builds
  it, to that use case's area; the name says which (`user_favorites.dart`).

### Inside a data area (`data/<area>/`)

One area, one repository. Only these files and folders exist (names:
[code-style.md](code-style.md), Files and types):

```
<area>_repository_impl.dart   # implements domain/repository/<area>_repository.dart
data_source/                  # data sources, their exceptions and DI modules, one of each per type
model/                        # DTOs only: freezed + json
mapper/                       # DTO or SDK type -> entity
```

- **Data source types**, a closed list: `api` (retrofit client), `hive`, `prefs`
  (`SharedPreferencesAsync`), `fcm` (`FirebaseMessaging`), `notif`
  (`flutter_local_notifications`), `firebase` (`FirebaseAuth`). A new type is added here and
  to `_dataSourceTypes` in `tool/check_imports.dart`.
- A repository reaches an SDK, a client or storage only through its data sources. A data
  source translates the SDK exceptions the repository must tell apart into its own exception,
  so the repository imports no SDK.
- The DI module of a type provides the SDK that the data source of that type wraps
  (`auth_firebase_module.dart`: `FirebaseAuth`). A port of `data/_shared` is implemented
  by the data source of the area that owns the SDK: `AuthFirebaseDataSource` implements
  `TokenProvider`, bound in `auth_firebase_module.dart`.

`data/_shared` has only three folders, by role like `domain/_shared`:

- `base/<subject>/`: base classes of the data layer, in a folder named after the classes that
  implement them (`base/data_source/expiring_cache.dart`).
- `data_source/`: what the data sources of all areas share, one folder per technology
  (`network/`, `hive/`, `prefs/`). It has no data source of its own, so the naming rules of an
  area's `data_source/` do not apply to it.
- `service/`: one folder per service, named like its folder in `domain/_shared/service/`,
  holding the implementation and the DI module of its SDK.

The checker enforces the three folder names, that `base/` declares no plain `abstract class`,
and the `service/` layout; the layout of `data_source/` is checked in review.

### Inside a feature (`presentation/<feature>/`)

```
bloc/              # *_bloc.dart, *_event.dart, *_state.dart, and pure Dart code the Blocs use
page/              # *_page.dart (one per route)
widget/            # feature-private widgets
```

Pure Dart code in `bloc/` is input validators (`auth/bloc/auth_validator.dart`) and their
error enums, which the states carry and the widgets read (`auth/bloc/auth_field_error.dart`).

### Inside `presentation/_shared`

```
theme/                  # AppTheme light/dark (Material 3)
  const/                # design constants: app_spacing.dart (AppSpacing)
l10n/                   # context.l10n extension, failure -> message mapping, appLocalizationsDelegates
component/<subject>/    # components, by what they do: favorite_toggle/
widget/<type>/          # plain widgets, by widget type: dialog/, image/, state/, tile/
```

A folder is created with its first file.

- **A component** is used by several features and has a Bloc or a page of its own. It has the
  layout of a feature (`bloc/`, `page/`, `widget/`) but no route: `app` builds the route of a
  shared page. Its Bloc is a factory (Dependency injection), so every place that shows the
  component gets its own instance. State that several features must see together never goes
  through a component: each Bloc follows the same domain repository stream, as the favorite
  toggle does. Shared UI state that belongs to no domain area is not decided yet: ask before
  choosing.
- **A plain widget** has no Bloc. When a widget gets one, it moves to `component/`.
- A widget of an area that has no feature of its own and is shown only by `app` lives here too
  (the notification permission dialog in `widget/dialog/`), so removing the area does not
  touch the screen that shows it.

## Import rules

Enforced by `tool/check_imports.dart` in CI.

### Between top-level folders

| Folder | May import | Must not import |
|---|---|---|
| `shared/` | allowed packages (External packages) | any layer, `app`, `l10n` |
| `domain/**` | `shared/`, `domain/**` (Inside domain, below), allowed packages | `data`, `presentation`, `app`, `l10n`, Flutter, `dart:ui`, `dart:io`, `dart:ffi`, `dart:isolate`, `dart:html` |
| `data/**` | `shared/`, from `domain` only its own contract, entities and wrappers (Inside data), `data/_shared`, its own packages | `presentation`, `app`, `l10n`, presentation packages, Flutter UI |
| `presentation/**` | `shared/`, from `domain` only use cases (Bloc files), entities and wrappers (Inside presentation), `presentation/_shared`, `l10n`, its own packages | `data`, `app`, data packages |
| `l10n/` | `flutter`, `flutter_localizations`, `intl` | everything else |
| `app/` | everything | — |

`main.dart` counts as `app`. Files outside these folders are rejected.

### Libraries and code

- `data` uses only `flutter/foundation.dart` and `flutter/services.dart` from Flutter.
- Bloc files (`*_bloc.dart`, `*_state.dart`, `*_event.dart`) use only
  `flutter/foundation.dart` from Flutter and none of the design packages (`material_ui`,
  `cupertino_ui`), so they never see a `BuildContext`.
- Widgets import Material from `package:material_ui/material_ui.dart`, never from the
  deprecated `package:flutter/material.dart` ([tech-stack.md](tech-stack.md), Compatibility
  notes). `flutter analyze` reports the old import; the import checker does not.
- `getIt`, `GetIt` and `GetItHelper` appear only in `app/`. The checker searches for the names,
  because `injectable.dart` re-exports `GetItHelper`.

### File locations

- `*_dto.dart` and `*_repository_impl.dart` live in `data`, `*_use_case.dart` in a group folder
  of `domain/use_case`, `*_bloc.dart` in `presentation`.
- No `use_case` folder under `presentation/`.
- `domain` has only the folders of Inside `domain`; a data area only the files and folders of
  Inside a data area. A use case group is an area with a contract in `domain/repository/`, or
  `observability` (`_serviceUseCaseGroups` in `tool/check_imports.dart`).

### Inside domain

| Folder | May import from `domain` |
|---|---|
| `_shared/base/` | `_shared/base/`, `_shared/wrapper/` |
| `_shared/service/` | `_shared/service/` |
| `_shared/wrapper/` | `_shared/wrapper/` |
| `entity/` | `entity/` |
| `repository/` | `entity/`, `_shared/wrapper/`; never another contract |
| `use_case/` | everything except another use case |

Who imports a part of `domain` from outside it:

- `_shared/wrapper/` and `entity/`: every layer.
- `_shared/base/`: only use cases.
- `_shared/service/`: only use cases, `data/_shared/service` and `app`. `app` imports only
  `crash_reporting_service.dart` (`_appServicePorts` in `tool/check_imports.dart`), to report
  errors; analytics from `app` goes through a use case (`TrackScreenViewUseCase`). Generated DI
  code (`injection.config.dart`) is exempt.
- `use_case/`: only Bloc files and `app`.

Areas are combined only in use cases: a use case may use the contracts of any area, a contract
never imports another contract. Data that belongs to a user takes the user id in every
repository call, and a use case supplies the current user (`WatchFavoritesUseCase`,
[area/favorite.md](area/favorite.md)).

### Inside data

- `data/<area>` imports from `domain` only `repository/<area>_repository.dart`, `entity/` and
  `_shared/wrapper/`. `data/_shared/service` may also import `domain/_shared/service/`.
- A repository implementation imports no external package other than `injectable`, `talker`,
  `stream_transform`, `meta` and `collection`.
- Areas do not import each other: `data/character` never imports `data/auth`.
- Each data source and API client belongs to the repository of its area.

### Inside presentation

- A Bloc file imports from `domain` only `use_case/` (any group), `entity/` and
  `_shared/wrapper/`; every other `presentation` file only `entity/` and `_shared/wrapper/`.
- Features do not import each other. A screen that needs data from several areas stays one
  feature with several Blocs, each depending on its own use cases.

### Shared folders

- `<layer>/<x>` may import `<layer>/_shared` (`data`, `presentation`).
- `<layer>/_shared` never imports an area or a feature of its layer.
- Inside `presentation/_shared`, all subfolders may import each other: the checker treats
  `_shared` as one area.

### Reserved names

`shared` and `_shared` cannot be area or feature names.

### External packages

- **Allow list** for `shared`, `domain` and `l10n` (`_allowedPackages` in
  `tool/check_imports.dart`). `shared`: `injectable`, `talker`, `meta`, `collection`.
  `domain`: `freezed_annotation`, `meta`, `collection`, `stream_transform`, and from
  `injectable` only `package:injectable/injectable.dart`.
- **Package ownership** for `data` and `presentation`: each package belongs to one of them,
  and the other layer must not import it.
  - The layer that imports a package first owns it; a new package needs no checker change.
  - A package imported by both layers fails unless it is in `_sharedPackages`: `flutter`,
    `freezed_annotation`, `injectable`, `stream_transform`, `meta`, `collection`.
  - `_knownOwners` fixes the owner in advance, so a first import in the wrong layer fails too.
    Data: `dio`, `http`, `retrofit`, `hive_ce`, `hive_ce_flutter`, `shared_preferences`,
    `sqflite`, `drift`, `firebase_*`. Presentation: `flutter_bloc`, `bloc`,
    `bloc_concurrency`, `material_ui`, `cupertino_ui`.

Deciding the layer of a new package:

1. It reaches the network, storage, a platform SDK or Firebase: `data` (add it to
   `_knownOwners` if it is widely known).
2. It draws UI or holds UI state: `presentation`.
3. Both layers really need it (annotations, pure utilities): `_sharedPackages`. Keep this list
   short: every entry links the layers.
4. Only `app` uses it (startup, links, app info): no change.

## Data flow

```
Page -> Bloc -> UseCase -> Repository (domain, abstract)    UseCase -> Service (domain, abstract)
                                ^                                         ^
               RepositoryImpl (data) -> <area>_api_data_source (retrofit)  Firebase<X>Service (data/_shared/service)
                                     -> <area>_hive_data_source, <area>_prefs_data_source, …
```

- A Bloc calls only use cases, also when a use case only passes the call to a repository
  (`SignOutUseCase`).
- `app` calls use cases for business actions and reaches repositories and services directly
  only for DI, bootstrap, cache eviction and error reporting
  (`CrashReportingService.recordError` in the error handlers and the Talker observer).
- A use case holds the logic: combining repositories, business rules and validation, analytics
  events. The format of form input (empty, email format, length, matching fields) is validated
  in the Bloc.

## Use cases

- One use case per file in its group folder, with one public method, `call`.
- Every use case implements one base class from `_shared/base/use_case/`: `UseCase<T, P>`
  (`Future<Result<T>> call(P params)`, never throws) or `StreamUseCase<T, P>`
  (`Stream<T> call(P params)`).
- `P` is always a record, also for one parameter (`({int id})`); without parameters it is
  `()`. A call reads `getCharacterDetail((id: 5))`, `watchFavorites(())`.
- A use case never imports another use case.
- **Analytics events are sent only from use cases.** A use case sends the event of the business
  outcome it produces (`AnalyticsEvent.signedIn()` in `SignInUseCase`); a fact only the UI
  knows is sent by a `Track<Event>UseCase` that the Bloc calls at the right moment (after the
  debounce, not on a retry: `TrackSearchUseCase`, CHR-17).

## Result and failure

`Result` and `Failure` live in `domain/_shared/wrapper/result`. `Result<T>` is a sealed class
with two variants: `Ok(value)` and `Err(failure)`.

`Failure` is a sealed hierarchy: `NetworkFailure`, `ServerFailure(statusCode)`,
`NotFoundFailure`, `CacheFailure`, `AuthFailure` (with an `AuthFailureReason` enum),
`UnexpectedFailure`.

- Every repository contract returns `Result<T>` or `Stream<T>`; repositories and use cases
  never throw.
- Exceptions become a `Failure` only in `data`: by `safeCall()` in
  `data/_shared/data_source/network` for network calls, and by the repository's own guard for
  its other sources. A data source translates the SDK exceptions the repository must tell
  apart into its own exception type (`AuthFirebaseException` with its `Failure`).
- Each error is logged once, where it is converted, and never swallowed silently.
- A failure becomes a user message only in `presentation/_shared/l10n`.

## Entities and DTOs

| | Location | Tools | JSON |
|---|---|---|---|
| Entity | `domain/entity` | freezed | No |
| DTO | `data/<area>/model` | freezed + json_serializable | Yes |
| Mapper | `data/<area>/mapper` | extension `toEntity()` / `fromEntity()` | — |

freezed 4: classes are `sealed` or `abstract`; constructor parameters have no `final`.

## Paginated data

`Paginated<T>` in `domain/_shared/wrapper/pagination`: `items`, `page`, `hasMore`. Pagination
details of a specific API stay in `data`.

## Dependency injection

- Registration with annotations next to each class: repositories
  `@LazySingleton(as: XRepository)`, use cases and Blocs `@injectable` (factory).
- Blocs are created in the route builders in `app/router/routes.dart` with
  `BlocProvider(create: (_) => getIt<XBloc>())`.
- Global singletons: `AuthBloc`, `SettingsBloc` (`@lazySingleton`). `app` provides
  `SettingsBloc` above `MaterialApp` and passes `AuthBloc` to the router, its only reader.
  Other features depend on use cases instead.
- Classes receive dependencies through their constructors.
- Objects that cannot carry an annotation come from DI modules, next to the code that owns
  them. **In `data`, one module per SDK:** it provides the objects of one SDK and binds ports to
  the class that wraps it (`TokenProvider` in `auth_firebase_module.dart`):
  - `shared/logging/logging_module.dart`: Talker;
  - `data/_shared/data_source/hive/hive_module.dart`: Hive;
    `data/_shared/data_source/prefs/prefs_module.dart`: `SharedPreferencesAsync`;
  - `data/_shared/service/analytics/firebase_analytics_module.dart`: Analytics;
    `data/_shared/service/crash_reporting/firebase_crashlytics_module.dart`: Crashlytics;
  - `data/<area>/data_source/<area>_<type>_module.dart`: an SDK that one area uses
    (`FirebaseAuth` in `data/auth`; `FirebaseMessaging` and the local notifications plugin in
    `data/notification`, one module each);
  - `app/di/config_module/`: everything that needs the flavor config (Dio clients, the
    character cache TTL, the usage data default).
- `getIt.init` receives the flavor name as the environment. No registration uses
  `@Environment` yet; add it when a class differs per flavor.

## State management

"Bloc" is the class, "flutter_bloc" the library.

- Every state holder in `presentation` is a `Bloc`; `Cubit` is not used.
- Events are a sealed class per Bloc with `final` subclasses and `const` constructors, without
  freezed. Events carry data only, never callbacks. Tests match an event with
  `isA<E>().having(...)`.
- An event that carries a secret overrides `toString()` to show the other fields only
  ([security.md](security.md), Logs and reports).
- States are freezed sealed classes or a single freezed class with a status enum.
- The state changes only through events: a Bloc has no public members besides its
  constructor, `close()` and constants (`CharacterListBloc.searchDebounce`, read by tests).
- **Every `on<E>` passes `transformer:`**, also for synchronous handlers (`bloc_concurrency`):
  - `droppable()`: a repeat is ignored while one runs (submit, toggle, sign-out);
  - `sequential()`: every event runs, in order (saving settings);
  - `restartable()`: the newest event cancels the running one (loading, subscriptions);
  - `concurrent()`: only with a comment saying why overlapping runs are safe;
  - a custom transformer (debounce for search) is defined next to its Bloc and moves to
    `presentation/_shared` on second use.
- **Events that conflict across types** (they change the same part of the state and can
  overlap) go through one handler for their sealed group with one transformer
  (`ProfileAction`, `SettingsEvent`). When that does not fit, the handler keeps a generation
  counter in the state and drops a result whose counter is no longer current
  (`CharacterListBloc`, CHR-5).
- **External streams** are followed with `emit.forEach` or `emit.onEach` in a `restartable()`
  handler, never with `listen` or a `StreamSubscription`. A Bloc whose stream needs no argument
  adds its start event in its constructor (`AuthBloc`); otherwise its creator adds it
  (`FavoriteToggleStarted(characterId)` in the route builder).
- A handler cancelled by its transformer or by `close()` emits nothing more, so handlers need
  no `isClosed` checks.
- Checked by `tool/check_imports.dart` in all of `lib/`: no `Cubit` class and no
  `*_cubit.dart` file, a `transformer:` on every `on<E>`, no `listen` or `StreamSubscription`
  in `*_bloc.dart`. The checker reads text and skips only lines that start with `//`, so a
  trailing or block comment can mislead it. The rest is checked in review.

## Routing

go_router with go_router_builder. Route map and redirects:
[behavior/navigation.md](behavior/navigation.md).

- **Features never navigate by themselves.** A page receives navigation callbacks in its
  constructor (`onCharacterSelected(int id)`), and its route builder in
  `app/router/routes.dart` implements them with typed routes
  (`CharacterDetailRoute(id: id).go(context)`). Features stay free of `app` and of each other.
- Routes and navigation callbacks take ids, never domain objects.
- A page that shows a widget with its own Bloc (the favorite toggle on each tile) takes a
  builder in its constructor, and an optional builder for an action from another feature; the
  route builder implements it with `BlocProvider(create: (_) => getIt<...>())`.
- `AuthBloc` is read by the top-level redirect on each navigation, only to keep signed-in
  users off the auth routes. The router has no `refreshListenable`: auth changes do not
  navigate; the Profile page follows them through `ProfileBloc`.
- A route builder that must react to a Bloc state once (the notification permission after the
  first loaded character, NTF-1) wraps the page in a small widget with a `BlocListener`.
- Screen views are sent by `ScreenViewObserver` in `app/router` through
  `TrackScreenViewUseCase`, with route names
  ([area/observability.md](area/observability.md), Screen views; what a name may carry:
  [security.md](security.md), Personal data).

## Networking

- Two Dio clients, created in `data/_shared/data_source/network`: `publicDio` for third-party
  public APIs, without `AuthInterceptor`, and `backendDio` for the app's own backend, with
  `AuthInterceptor`. Where the token may go and what the logs may hold:
  [security.md](security.md), Tokens; Logs and reports.
- Both have connect and receive timeouts (`dio_factory.dart`); a timeout becomes
  `NetworkFailure`. A slow request overrides them through its own `Options`.
- A 401 from the own backend refreshes the token once and retries; a second 401 signs the
  user out.
- Only GET and HEAD are retried, only for transient errors, with a short bounded backoff.
- **One remote call, one place** (retrofit methods and Firebase calls). Before adding one,
  search the data sources in `data/*/data_source/` for a call that fetches or sends the same
  data. If there is one, a use case reaches it through its area's repository (add a repository
  method if none exposes it); never copy the call into another area. A new call goes into the
  data source of the area that owns the data; a new data source is created only for an area
  that has none of that type. Checked in review.
- `TokenProvider` is a port in `data/_shared/data_source/network`; `AuthFirebaseDataSource`
  implements it with Firebase Auth.
- Interceptor steps, retried statuses, numbers and chain order:
  [area/network.md](area/network.md).

## Local storage

| Data | Kind | Storage | Why |
|---|---|---|---|
| Settings (theme, locale, usage data sharing) | Settings | `SharedPreferencesAsync` | Few scalar values, needed at startup |
| Notification permission flag (`notification.permission_requested`) | Settings | `SharedPreferencesAsync` | One boolean |
| Characters (API responses) | Cache | hive_ce `LazyBox`, JSON strings ([area/character.md](area/character.md)) | Many records, TTL, keyed by request |
| Favorites | User data | hive_ce `LazyBox` per user, JSON strings ([area/favorite.md](area/favorite.md)) | Persistent snapshots of characters, separated by user |

- Each storage is wrapped by a data source of its type (`<area>_hive_data_source.dart`,
  `<area>_prefs_data_source.dart`); nothing outside `data` knows about Hive or
  SharedPreferences.
- Hive values are JSON **strings** (`jsonEncode` of a DTO's `toJson()`), never maps, with no
  type adapters and no `hive_ce_generator`.
- Every stored value is wrapped in an envelope DTO with `schemaVersion` (`CachedRecordDto<T>`,
  `FavoriteRecordDto`); the data source checks `schemaVersion` on the decoded map before
  `fromJson`.
- Hive lower-cases box names, so a case-sensitive part of a name (a user id) is stored in hex.
- What may be stored, and encryption: [security.md](security.md), Local storage.

### Cache or user data

Every Hive store is one of two kinds. Decide before writing the data source: **if this data is
lost, can it be fetched again?** Yes: a cache. No: user data. When unsure: user data.

| | Cache (example: characters) | User data (example: favorites) |
|---|---|---|
| Origin | A copy of server data | Created by the user; no other copy |
| Marker in code | Data source `implements ExpiringCache` | Doc comment "User data"; never `ExpiringCache` |
| Box | Its own, named `<area>_cache` | Its own; never shared with a cache |
| Storage failure | Logged; the record counts as missing | Reaches the caller |
| Automatic deletion | Yes: records older than the cache's `maxAge` (set in its area file), with another `schemaVersion` or unreadable, after startup | **Never** |
| Who deletes | The app | Only a user action (remove a favorite, delete the account) |
| DTO change | Bump `schemaVersion`; old records are ignored, then evicted | Stay backward compatible (`@JsonKey(defaultValue: ...)`) or ship a migration; an unreadable record is skipped, logged and kept |

- Every cache is listed in `_evictExpiredCaches` in `app/bootstrap.dart`, which runs
  `evictExpired()` after the first frame. `tool/check_imports.dart` rejects a class in `data`
  that implements `ExpiringCache` and is missing from that list. Freshness is a separate,
  much shorter TTL in the repository; `maxAge` only limits how long stale data can still be
  shown offline.
- User data of a signed-in user is deleted with the account: add its cleanup to
  `DeleteAccountUseCase` ([area/profile.md](area/profile.md)).

## Testing

| Layer | What to test | Tools |
|---|---|---|
| domain | every use case, entity logic | `test`, mocktail, fakes of repositories and services |
| data | repositories (mapping, caching, failures), mappers, interceptors, data sources, reading stored records of the current format | mocktail, Dio mock adapter |
| presentation | Blocs: each state transition and the concurrency policy of each handler (a repeated event while one runs, or two events in quick succession); widget tests for critical flows (sign-in validation, list states) | bloc_test, `flutter_test` widget tests |

- A Bloc test builds the real use cases over mocked or fake repositories and services, so it
  also checks what the use case sends. A requirement about an analytics event has a use case
  test that the event is sent and a Bloc test that it is sent only when the requirement says
  so.
- Mocks are created with mocktail; `registerFallbackValue` lives in shared helpers under
  `test/helper/`.
- Firebase is never called in tests; it sits behind repositories and ports.
- Each screen's page test calls `testAccessibility` (`test/helper/accessibility.dart`), which
  checks ACC-1 to ACC-4 ([behavior/accessibility.md](behavior/accessibility.md)) in the
  screen's main state. `tool/check_imports.dart` checks that every `*_page.dart` in
  `lib/presentation/` has its page test at the mirrored path and that it calls
  `testAccessibility`; it reads text and skips only lines that start with `//`.
- Test names carry requirement IDs ([doc/README.md](../README.md), Requirements); test file
  paths: [code-style.md](code-style.md), Files and types.
